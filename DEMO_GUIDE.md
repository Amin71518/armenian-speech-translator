# Подготовка демонстрации Mathrix

Выбран текущий вариант с `--experimental-speaker-matching`, с известными
ограничениями. Демонстрация должна показать фактический результат, а не обещать
подтверждённые5секунд или безошибочные личности. GitHub оформляется последним.

## Перед интервью

1. Подключить питание и нужные наушники. Модели и окружение уже должны быть
   подготовлены по README; не начинать загрузку весов во время демонстрации.
2. В приложении звонка выбрать нужные микрофон и выход. В текущей конфигурации
   программа использует встроенный микрофон; звук собеседников идёт в OnePlus Buds3.
3. Проверить актуальные IDs:

   ```powershell
   poetry run python -m armenian_speech.combined --list-devices
   ```

   Две библиотеки имеют разные списки. ПоследниеIDs: встроенный mic14, Buds loopback16,
   Realtek loopback17. Подключение устройства меняет нумерацию.
4. Открыть оригинальные проектные чаты в Codex и иметь доступ к `chats/`.
   Не удалять и не архивировать историю перед интервью.
5. Открыть README, DECISIONS и comparison documents. Проверить наличие последнего
   `VALIDATION_REPORT.md`. Самостоятельно не запускать probes, которые включают
   микрофон или playback: для обычной демонстрации достаточно основного приложения.

## Запуск и короткий разговор

Для встроенного микрофона и Buds, после проверкиIDs:

```powershell
poetry run python -m armenian_speech.combined --microphone-device 14 --device 16 --diarize --experimental-speaker-matching
```

Дождаться `Combined live active`. Сначала говорить самому; затем два человека со
стороны звонка говорят по очереди и возвращаются к разговору. Дать каждому как
длинную фразу, так и короткий ответ, чтобы показать реальное ограничение длины.
Микрофон должен быть Me. System может дать Speaker1/2 или Unknown; не обещать,
что номера всегда соответствуют людям без проверки по голосам.

Если возникают ошибки, назвать наблюдение: поздняя регистрация, Unknown, лишний
ID, неверное HY или неверный EN. Не менять пороги в ходе разговора, чтобы скрыть
результат. Для отдельной диагностики остановить процесс и добавить
`--speaker-diagnostics`; этот флаг показывает scores/reasons и итоговый summary.

Ctrl+C один раз, дождаться завершения принятых задач. Штатный Python exit130
ожидаем; Poetry на Windows может показать1. Ошибки/forced termination/unfinished
не считать нормальным закрытием. Разговор сам по себе не сохраняется; короткий
WAV-мост для ASR существует временно в.cache/live и удаляется при штатной очистке.

## Как объяснить архитектуру за две минуты

- Звук принимают sounddevice и PyAudioWPatch WASAPI. Callback только копирует
  блоки и считает потери; модели не работают в callback.
- Каждый источник имеет отдельный ресемплер и Silero VAD. Готовые сегменты идут
  через ограниченные очереди и fair dispatch в один spawn worker.
- Только System проходит CAMPPlus speaker tracker. Me сохраняется в metadata
  каждой задачи. ID живут в пределах сессии, а не привязаны к именам людей.
- FastConformer INT8 распознаёт HY; NLLB greedy переводит HY в EN. Выбор сделан
  по отдельным сравнениям, чтобы ошибки ASR не подменяли оценку переводчика.
- Parent печатает HY/EN вместе после перевода. Ctrl+C имеет общий shutdown deadline;
  при overload incoming work отбрасывается явно, со счётчиками.

Для code walkthrough: `combined.py` → `fair_queue.py` → `live_pipeline.py`;
`speakers.py` для matching; `asr_onnx.py`/`translation.py` для моделей;
`tests/test_speaker_diagnostics.py` и `tests/test_live_pipeline.py` для проверок.

## Как объяснить ограничения

- **5 секунд** — целевой предел из задания. Измерение от VAD decision не включает
  ожидание границы VAD; физический speech-end E2E не подтверждён.
- Unknown означает недостаточную/противоречивую информацию для личности, а не
  отсутствие речи. Полезный текст продолжает распознаваться.
- Trial помогает регистрировать голос по1.5s реплике, но более короткая реплика
  новый ID не создаёт. Двухсекундные speaker cells и вынужденные границы могут
  разрезать слово; overlap/channel changes не решены.
- Публичные A/B файлы подтвердили воспроизводимый сбой и локальное улучшение,
  но это повторы двух отрывков, не независимая оценка всех армянских звонков.
- На последнем звонке12/12jobs завершились без зарегистрированных потерь, но
  8 из 14 System частей получили Unknown. Это нужно показать вместе с удачными фрагментами.

Не выдавать улучшение на примерах или успешные unit tests за доказательство
полного выполнения требований. Приоритеты дальнейшей работы перечислены в README.
